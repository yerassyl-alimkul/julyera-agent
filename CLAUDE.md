# JulYera Agent: контекст проекта

Личный ИИ-агент для управления задачами на нескольких человек (Yera и допущенные им люди, сейчас жена).
У каждого свои задачи, заметки, подзадачи, Telegram-чат и Google Calendar; вход через Telegram (см. «Модель доступа»).
Пользователь пишет или наговаривает задачу, Groq превращает текст в структурированную задачу,
она сохраняется в Supabase и показывается в Telegram-боте, веб-интерфейсе и Google Calendar.

Файл написан по памяти из длинного чата и мог устареть. Если он расходится с кодом, верь коду
и поправь этот файл.

## Как работать с владельцем

- Отвечай по-русски.
- Владелец хорошо понимает продукт, но терминал, git и инфраструктуру знает слабо.
  Перед командами коротко объясняй, что они делают, и не склеивай несколько команд в одну строку.
- Каждый `git push` в `main` сразу деплоится в прод (Render). Перед пушем спрашивай подтверждение.
- Никогда не выводи и не коммить значения ключей и содержимое `.env`.
  Если секрет попал в чат или лог, скажи, что его надо перевыпустить.

## Стек

- Backend: Python 3.12, FastAPI + uvicorn (`main.py`).
- База: Supabase (Postgres) через `supabase-py` с ключом `service_role` (RLS обходится).
- LLM: Groq. Разбор текста в задачи (модель задана константой `MODEL` в `groq_client.py`),
  голосовые сообщения распознаёт `whisper-large-v3`.
- Клиенты: Telegram-бот, веб-интерфейс `web/index.html` (чистый JS, без сборки).
- Хостинг: Render, бесплатный Web Service, адрес `https://julyera-agent.onrender.com`
  (он же зашит в `reminders.yml` и как запасной `BASE_URL` в `web/index.html`).
  После простоя засыпает, холодный старт до ~50 секунд.
  Версия Python закреплена переменной `PYTHON_VERSION=3.12.7` в Render (`runtime.txt` Render игнорирует, поэтому его в репозитории нет).
- Расписание: `/internal/reminders/run` зовут снаружи — cron-job.org каждые 15 минут (настроен владельцем
  8 октября 2026, POST с заголовком `X-Reminder-Secret`) и
  прежний GitHub Actions (`.github/workflows/reminders.yml`, 3 раза в день; файл не редактировать — нужен PAT
  со scope `workflow`). Частые вызовы заодно не дают Render засыпать.
- Календарь: Google Calendar API (OAuth, scopes `calendar.events` и `calendar.calendarlist.readonly`).

## Структура

- `main.py`: все HTTP-маршруты, зависимость входа `current_user`, webhook Telegram, раздача статики.
- `telegram_auth.py`: проверка подписи initData Telegram Mini App. `users_service.py`: пользователи и их чаты.
- `task_service.py`: логика задач (создание, обновление, повторяющиеся, синхронизация с календарём).
- `digest_service.py`: `/today`, утренняя и вечерняя сводка, напоминания с кнопками, отложенные задачи, перенос на завтра,
  напоминание перед задачей, итоги недели, «завтра спишется», когда слать резервную копию.
- `backup_service.py`: резервная копия данных одного пользователя файлом JSON (воскресенье 21:00 и `/backup`).
- `notes_service.py`, `subtasks_service.py`: CRUD заметок и подзадач. Список с галочками — строки «- [ ] …» / «- [x] …»
  прямо в тексте заметки (галочка = PATCH текста), ссылки — обычный текст. Фото заметок (миграция 013): `note_files`,
  файлы в бакете `task-files` (`<user_id>/notes/<note_id>/<id>.<ext>`), `POST /notes/{id}/files`, `DELETE /note-files/{id}`,
  в `GET /notes` у заметки `files` с подписанными ссылками на час; удаление заметки удаляет и файлы. `categories_service.py`: свои категории пользователя.
- `comments_service.py`: комментарии к задачам (текст, фото, PDF; файлы в Supabase Storage, бакет `task-files`).
- `money_service.py`: учёт расходов и доходов (категории денег, операции, итоги, повторяющиеся платежи, «деньги или задача»).
- `google_calendar_service.py`: OAuth и события календаря (задачи → события).
- `calendar_sync.py`: обратное направление — события Google Calendar → задачи (см. договорённость 7).
- `groq_client.py`: промпт `SYSTEM_PROMPT`, разбор текста, распознавание голоса.
- `telegram_handlers.py`: обработчики бота (`/start`, `/list`, текст, голос), общие для polling и webhook.
- `bot.py`: локальный запуск бота в режиме polling.
- `models.py`: Pydantic-модели. `database.py`: клиент Supabase. Он переключён на HTTP/1.1 (`_force_http1`): HTTP/2 у
  postgrest и storage3 под параллельными запросами рвал соединение (`RemoteProtocolError: ConnectionTerminated`,
  ~2% случайных 500 на проде, 9 октября 2026). При обновлении supabase-py проверь, что заплатка ещё применяется.
- `schema.sql`: журнал миграций (не скрипт для повторного запуска). Новые миграции дополнительно отдельными
  файлами `migrations/NNN_name.sql`; изменения схемы только добавляющие, SQL выполняет владелец.
- `web/index.html`: весь фронтенд в одном файле (светлый мобильный дизайн, см. ниже «Фронтенд»).
- `scripts/isolation_check.py`: проверка изоляции данных между пользователями (+ `scripts/fake_supabase.py`, база в памяти).
  `scripts/money_check.py`: проверки денег (те же два режима, плюс `--model` — разбор фраз настоящей моделью Groq).
  `scripts/digest_check.py`: проверки сводок и напоминаний (только локально, время подставное).
  `scripts/calendar_check.py`: перенос событий Google Calendar в задачи и обратно (только локально).
  `scripts/tasks_check.py`: точные повторы, «Разбей на шаги», задачи из заметки и `/split` (только локально).
  `scripts/goals_check.py`: цели накопления, `/save`, копия (только локально).
  `scripts/extras_check.py`: время «до», пять валют, выписка, диктовка, копия в бот (только локально).
  `scripts/notes_payments_check.py`: платёж «по галочке» и фото у заметок, миграция 013 (только локально).
  `scripts/shared_check.py`: совместные задачи, место, поиск адреса, галочка у платежа, миграция 014 (только локально).
- `design/`: спецификация нового дизайна `DESIGN.md` (раздел 12 — решения владельца), макеты `reference/*.dc.html`,
  тестовый сервер `mock_server.py` с подставными данными, `dev_server.py` — настоящий backend на базе в памяти
  с вымышленными задачами и деньгами (http://localhost:8002/?key=test123, конфигурация `dev` в `.claude/launch.json`).
- `migrations/NNN_name.sql`: новые миграции отдельными файлами (001 — деньги, 002 — сводки, 003 — кошелёк и Apple Pay,
  004 — лимиты и месячный отчёт, 005 — комментарии к задачам и хранилище файлов, 006 — перенос событий календаря, 007 — его выключатель, 008 — выбор календарей, 009 — напоминание перед задачей,
  «завтра спишется» и резервная копия, 010 — точные повторы задач, 011 — цели накопления, 012 — время «до» и пять валют, 013 — фото у заметок и платёж «по галочке», 014 — место и совместные задачи).
- `release_notes.py`: заметка о релизе, которую бот присылает владельцу после деплоя.
- `rates_service.py`: курс валют Нацбанка РК для пересчёта итогов в основную валюту.
- `goals_service.py`: цели накопления (миграция 011, см. «Деньги»).
- `shared_service.py`: совместные задачи (договорённость 10). `places_service.py`: подсказки адреса для «Места»
  (OpenStreetMap Nominatim через сервер: не чаще запроса в секунду, свой User-Agent, кэш в памяти на сутки).
- `statement_service.py`: выписка по кошельку в PDF (reportlab, шрифты Onest и Unbounded в `assets/fonts`, OFL).

Маршруты: `/tasks` (+ `/tasks/parse`, `/tasks/{id}`), `/notes`, `/subtasks`, `/tasks/{id}/subtasks`, `/categories`,
`/money/categories|transactions|parse|summary|trend|recurring`, `/me`,
`/google/auth-url|auth|callback|status`, `/telegram/webhook/{token}`, `/internal/reminders/run`, `/health`.
Публичные только `/health`, статика, `/google/callback` (защищён подписанным `state`), `/telegram/webhook/{token}`
(защищён токеном в адресе) и `/internal/reminders/run` (заголовок `X-Reminder-Secret`); остальное требует входа.

`SUPABASE_URL`, `SUPABASE_KEY` (service_role), `GROQ_API_KEY`, `TELEGRAM_BOT_TOKEN`,
`WEBHOOK_BASE_URL` (только прод), `REMINDERS_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`,
`GOOGLE_REDIRECT_URI`, `OAUTH_STATE_SECRET` (подпись `state` при подключении календаря, случайная строка от 32 символов;

## База данных

- `users`: `id`, `name`, `telegram_user_id` (уникальный), `is_admin`, `access_key` (для ссылки `/web`).
  У `tasks`, `notes`, `telegram_chats` есть `user_id`; у `google_credentials` первичный ключ `user_id`
  (раньше одна строка `id = 1`). Миграция записана в конце `schema.sql`.
- `categories`: `user_id`, `name`, `color` (из палитры `categories_service.PALETTE`), `sort_order`; уникальность
  `(user_id, lower(name))`. Переименование — SQL-функция `rename_category` (меняет и задачи), вызывать её может
  только `service_role`.
- `tasks`: `task`, `category` (название категории пользователя текстом, без CHECK), `source`, `deadline` (timestamptz), `priority` (High | Mid | Low),
  `status` (To Do | In Progress | Done), `note`, `is_recurring`, `recurrence_pattern`, `tags` (text[]), `google_event_id`.
- `subtasks` (связь с `tasks` каскадом, своей колонки `user_id` нет), `notes`, `telegram_chats` (для напоминаний),
  `google_credentials` (по строке на пользователя).
- Деньги (`migrations/001_money.sql`): `users.default_currency` (EUR | KZT), `money_categories` (`kind` expense | income,
  уникально `(user_id, kind, lower(name))`), `money_transactions` (`amount numeric(14,2)`, `currency`, `spent_on date`,
  `source` app | text | voice | recurring, `recurring_id`), `money_recurring` (`day_of_month`, `next_run`, `active`).
  Уникальный индекс `(recurring_id, spent_on)` не даёт платежу создать операцию дважды. RLS включена.
- Миграции выполняются вручную в Supabase SQL Editor. Перед новой миграцией спроси владельца, что уже применено.
- В интерфейсе статус `In Progress` не используется: все не-Done задачи показываются вместе как «To Do», Done уходит в «Архив».

## Модель доступа (несколько пользователей)

- Backend ходит в базу с ключом `service_role`, который обходит RLS. Вся изоляция держится на условии `user_id`
  в каждом запросе к `tasks`, `notes`, `telegram_chats`, `google_credentials`; подзадачи проверяются через их задачу
  (`subtasks_service._owns_task`). Новый запрос без такого условия — дыра. Чужой `id` в маршруте даёт 404.
- `user_id` всегда ставит сервер из `current_user`; модели создания и обновления его не содержат, лишние поля
  от клиента игнорируются.
- Вход: заголовок `X-Telegram-Init-Data` (Mini App; подпись проверяется токеном бота, срок 24 часа) или
  `X-Access-Key` (ссылка `/web` для браузера). Нет входа или подпись неверна → 401; человек не допущен → 403
  `{"code": "not_approved"}`.
- Новых людей допускает владелец (`is_admin`): незнакомец пишет боту `/start`, владельцу приходит запрос с кнопками
  «Разрешить» / «Отклонить». Решение принимается по `from.id` нажавшего, повтор не дублирует пользователя,
  запрос не чаще раза в час (счётчик в памяти). Неизвестный чат ничего не создаёт.
- Google Calendar у каждого свой: токены по `user_id`, в `state` подписанная метка `user_id` на 10 минут
  (`make_state` / `verify_state`). Фронтенд берёт адрес через `/google/auth-url` и открывает его во внешнем браузере.
- Честный статус: `/google/status` → `{configured, connected, needs_reconnect}`; токен проверяется вживую
  (обновление access-токена), результат кэшируется на 10 минут. `invalid_grant` (RefreshError) и 401/403 от API
  ставят `google_credentials.needs_reconnect`, бот один раз пишет «переподключите», синхронизация пропускается;
  сеть, 5xx и 404 — временные сбои, только лог. Успешный callback снимает флаг. Задач до подключения не догоняем.
- Напоминания и сводки идут каждому пользователю в его чаты и только с его задачами. Кнопки «Готово» / «+1 ч»
  (`done:<id>`, `snooze:<id>`) и «Перенести» (`dmove:<день>`) проверяют пользователя по `from.id`: чужая задача — отказ.
- Категории у каждого свои: название 1–30 символов, уникально без учёта регистра; цвет только из палитры (8 цветов);
  хотя бы одна категория всегда есть (новому при одобрении — «Общее»), первая по порядку — запасная для парсера.
  `POST/PATCH /tasks` с чужой или несуществующей категорией → 422; удаление категории с задачами требует `move_to`
  (иначе 409). Парсер получает названия категорий пользователя, неизвестный ответ модели заменяется запасной.

## Деньги (учёт расходов и доходов)

- Суммы: в базе `numeric(14,2)`, в Python только `Decimal` (`money_service.parse_amount`, `fmt`), в JSON строкой
  `"1240.50"`; запятая принимается как десятичный знак. Никаких `float` в расчётах.
- Валюты (`money_service.CURRENCIES` = EUR, KZT, USD, AZN, TRY; миграция 012, решение 10 октября 2026): у пользователя
  пара — основная (`users.default_currency`) и дополнительная (`users.second_currency`, `money_service.second_currency`;
  совпадёт с основной — меняются местами). В формах траты и цели — только эти две (плюс валюта самой операции,
  `userCurrencies` во фронтенде), в боте и Apple Pay — любая из пяти. Экран «Валюты» (`currencySheet`) — две группы.
  Операция хранится в своей валюте и не меняется. Итоги по каждой
  валюте есть всегда (`currencies`), плюс блок `main` — всё в основной валюте пользователя (`users.default_currency`,
  кнопка «Валюта» в кошельке, `/currency` в боте), пересчитанное по сегодняшнему курсу Нацбанка РК (`rates_service`,
  кэш 6 часов, решение владельца 8 октября 2026: не по курсу дня траты). `approx` у категорий и дней и `parts`
  показывают, где был пересчёт (там в интерфейсе «≈»). Нет курса — `main: null`, интерфейс показывает итоги по
  валютам раздельно. В проверках курс постоянный (1 € = 500,35 ₸, `isolation_check.setup_local`).
  Добавить валюту: константа, CHECK в базе, `CURRENCY_MARKERS`.
- Дата операции — `date` («YYYY-MM-DD») без времени, ± 5 лет от сегодня; «сегодня» — в `users.timezone`.
  Во фронтенде разбирается по частям (`ymd`), не через `new Date(isoString)`.
- Итоги (`/money/summary`, `/money/trend`) читают базу порциями (`_fetch_all`, по 1000), иначе после 1000 операций
  суммы молча обрежутся. Интерфейс суммы не складывает: итоги, суммы дней и разницу с прошлым месяцем считает сервер.
- Категория операции — своя и того же `kind`, иначе 422; `move_to` при удалении — своя (иначе 404) того же типа (иначе 422).
- Повторяющиеся платежи (`money_recurring.frequency` weekly | biweekly | monthly | yearly, `anchor_date` — дата первой
  операции) создаются внутри `/internal/reminders/run` до рассылки (`run_recurring`, шаг — `advance`): догоняют до 12
  пропущенных периодов, 31-е в коротком месяце (и 29 февраля) даёт последний день, сбой одного платежа не мешает
  остальным и рассылке. Новое правило не создаёт операций задним числом (`_first_run_after`).
- В кошельке у каждого повторяющегося платежа кружок «оплачено» (`POST /money/recurring/{id}/pay`, `pay_now`:
  операция сегодня, срок — следующий; у платежа «по галочке» — то же, что галочка на его задаче; платёж на паузе
  снова в работе). Переключателя паузы больше нет, «Изменить / Удалить» — свайпом (удаление с отменой 5 с).
- Над вкладками кошелька — «<Месяц> · остаток» (`renderMoneyNet`, доходы − расходы из `/money/summary`).
  «Даты» в «Операциях» (`moneyRange`): список за свой период, суммы — `/money/analytics?from&to`.
- Платёж «по галочке» (миграция 013, решение владельца 11 октября 2026; переключатель у каждого правила
  «Записывать после галочки», `money_recurring.as_task`): `run_recurring` такой платёж не списывает, а держит одну
  открытую задачу «💳 Жильё · 500 €» на `next_run` 23:59 (`tasks.money_recurring_id`, `tasks.money_due` — срок,
  за который она; уникальный индекс — одна открытая задача на платёж). Done (`task_service.update_task` →
  `money_service.pay_from_task`) — операция сегодняшним днём (если сегодня уже есть операция этого правила —
  датой срока), `next_run` сдвигается условным обновлением `eq(next_run, money_due)` (повторная или одновременная
  галочка ничего не дублирует), ставится задача на следующий срок. Удаление открытой задачи — пропуск срока
  (`skip_payment`). Пауза, выключение «по галочке» и удаление правила убирают открытую задачу
  (`delete_task(..., payment_hook=False)`); выключили — `next_run` не раньше сегодня.
- Заметки о релизе: перед каждым релизом обнови `release_notes.py` (новый `RELEASE_ID` и текст по-русски). После деплоя
  сервер один раз присылает текст всем пользователям в бот (`release_log`, вставка до отправки). Так решил владелец:
  текст пиши понятно для любого пользователя, без технических подробностей.
- Бот: `/spent`, `/income` — всегда деньги, `/task` — всегда задача; без команды деньги — если число рядом с валютой
  (`looks_like_money`) или первое слово «расход»/«доход». Под операцией кнопки «Отменить / Категория / Это задача»
  (`callback_data` `m:…`, ≤ 64 байт; пользователь — по `from.id`, чужая операция — отказ). Меню команд ставится при
  запуске (`BOT_COMMANDS`, `set_my_commands`). Под полем ввода постоянная панель (`main_keyboard`: «Сегодня», «Все
  задачи», «Месяц», «Последние траты», «Помощь»): её текст `handle_text` узнаёт раньше разбора задач и денег

- Apple Pay: автоматизация «Транзакция» в «Командах» iPhone шлёт `POST /money/applepay` (заголовок `X-Access-Key`,

## Договорённости, которые нельзя ломать

1. **Время дедлайна хранится «голыми часами» без часового пояса.** Supabase отдаёт его с суффиксом `+00:00`,
   но это ложная метка. В Python перед передачей наружу снимай tzinfo (`replace(tzinfo=None)`; сейчас это делает только
   `_event_body` в `google_calendar_service.py`, остальной код берёт `.date()`/`strftime` и от метки не зависит),
   во фронтенде разбирай строку через `parseNaiveDeadline`. Не используй `new Date(isoString)` для показа времени,
   иначе время сдвинется на часовой пояс браузера.
2. **Часовой пояс пользователя** — колонка `users.timezone` (по умолчанию `Europe/Rome`, редактирования в интерфейсе нет),
   читается через `users_service.timezone_of`. По нему ставятся события Google Calendar (`_event_body`) и считается
   «сегодня» при разборе текста (`parse_text_to_tasks(..., timezone=...)`). Родной часовой пояс владельца Asia/Almaty.
   По нему же идёт расписание рассылок (`digest_service.SLOTS`): сводка 08:00, напоминания 13:00 и 17:00,
   итоги дня 20:00 — каждая в окне [время, +1 час) и один раз в день (строка в `digest_log` вставляется до отправки).
3. **Статика монтируется на `/` самой последней** в `main.py`, иначе она перекроет API-маршруты.
   HTML отдаётся с `Cache-Control: no-cache` (`html_no_cache`), чтобы после релиза телефон не показывал старую страницу.
4. **Polling и webhook у одного бота несовместимы.** Запуск `bot.py` локально снимает webhook у прод-бота.
   Пока работает прод, локально бота не запускай. Webhook возвращается при перезапуске сервиса на Render.
5. **Имена моделей Groq меняются.** Если Groq вернёт `model_not_found`, смени `MODEL` в `groq_client.py`.
6. Повторяющаяся задача при переводе в Done создаёт следующую (`task_service.next_occurrence`, миграция 010):
   `recurrence_pattern` daily | weekdays (пн–пт) | weekly (старое, +7 дней) | days (`recurrence_days` 0 = пн … 6 = вс)
   | monthly (того же числа, `recurrence_days = [число]`; 31-е в коротком месяце — последний день) | yearly.
   Прошедшие повторы пропускаются: следующий срок всегда позже сегодняшнего дня пользователя. `is_recurring` и
   дни ставит сервер (`_normalize_recurrence`, «по дням недели» без дней — 422). Во фронтенде блок «Повторять»
   в «Изменить» и «Вручную» (`renderRepeat`, подсказка `nextTaskRepeat` считает как сервер; у задач из Google
   блока нет), в строке задачи «↻ пн, ср» (`repeatLabel`). Копия переносит теги и дни и сразу получает своё событие
   в Google Calendar (`update_task` в `task_service.py`). Подзадачи не копируются.
6c. Время «с — до» и даты «с — по» (`tasks.ends_at`, миграция 012; «по» — 11 октября 2026): только при дедлайне и позже
   него (иначе 422). Задача на несколько дней видна на каждом своём дне в полосе дней и в календаре (`taskDayKeys`,
   не больше 62 дней), просрочена — после последнего дня; напоминание — по началу. «По» без времени — 23:59. Перенос задачи без
   «до» сдвигает конец на ту же длительность; копия повторяющейся — тоже. Событие Google — ровно до `ends_at`
   (иначе 30 минут), из Google `ends_at` приходит концом события. В формах — дата на всю ширину, ниже «с» и «до»;
   в списке «09:00–10:30» (`timeRange`). ИИ ставит `ends_at` только при явном «с … до …».
6a. «Разбей на шаги»: `POST /tasks/{id}/breakdown` → `groq_client.suggest_steps` (название, заметка, уже
   существующие шаги) → 3–7 подзадач сразу, без повторов. Кнопка в «Изменить» и в раскрытой карточке.
6b. Задачи из текста без сохранения: `POST /tasks/preview` (тот же разбор, что `/tasks/parse`). Кнопка
   «Задачи из заметки» в карточке заметки → список с галочками → отмеченные `POST /tasks` (`source: note`).
   В боте `/split текст` — то же с кнопками ☑️/⬜️ (`sp:<токен>:<n|ok|x>`, выбор помнится 15 минут).
7. Синхронизация с Google Calendar в обе стороны (решение владельца 9 октября 2026, миграция 006).
   Задачи → события: `google_calendar_service`; событие задачи JulYera удаляется при Done,
   при удалении задачи и при снятии дедлайна; у событий JulYera метка `extendedProperties.private.julyera = "1"`.
   События → задачи: `calendar_sync.run_all` в каждом `/internal/reminders/run` (до сводок) и сразу после
   подключения календаря. Основной календарь с начала сегодняшнего дня: все разовые события и каждое повторение
   повторяющихся на `RECURRING_DAYS` (30) дней вперёд — отдельной задачей (`gcal_imported`, источник «Google Calendar»,
   категория от Groq по названию, приоритет Mid). Прошлые, отклонённые, `workingLocation` и свои события JulYera
   (метка или старый префикс 🔴🟡🟢) не переносятся. Событие на весь день — задача на 23:59 (`gcal_all_day`).
   Правка в Google видна по `updated` события новее `tasks.gcal_updated` (его пишет и наша запись в календарь) —
   переносятся название, время, описание → заметка. Правка импортированной задачи в JulYera — `patch` события
   (длительность, место, гости сохраняются; `sendUpdates="none"`), её Done событие НЕ удаляет, удаление задачи — удаляет.
   Удалено в Google (`cancelled` или 404/410 на прямой запрос) — незакрытая задача удаляется, закрытая теряет ссылку;
   по одному отсутствию в списке ничего не удаляется. Уникальный индекс `(user_id, google_event_id)` против дублей.
   Выключатель в меню (под «Google Calendar подключён», `showCalendarImportSwitch`) — `users.calendar_import`
   (миграция 007, по умолчанию true; `PATCH /me {"calendar_import": …}`): выключено — это направление
   пропускается целиком, перенесённое остаётся; включили — `sync_after_connect` сразу фоном.
   Выбор календарей (миграция 008): `google_credentials.import_calendars` (пусто = только основной, id основного —
   "primary"), у задачи — `tasks.gcal_calendar_id` (пусто = основной; по нему идут get/patch/delete события).
   `GET /google/calendars` (список через `calendarList`, скрытые не показываются, `read_only` у чужих
   календарей), `PUT /google/calendars {"ids": […]}` — только свои id, сразу `sync_user`, ответ `created`.
   Экран `calendarsSheet` из строки «Из календарей: …» в меню. Права `calendar.calendarlist.readonly` добавлены
   9 октября 2026: старому подключению нужен один раз «Переподключить» (`needs_upgrade`), до того работает основной.
   `Credentials` создаются без `scopes`, иначе обновление старого токена падает с invalid_scope. 403 у не основного
   календаря (только чтение, закрыли доступ) — не повод для needs_reconnect, только лог. Снятый с выбора
   календарь: его задачи остаются и больше не синхронизируются.
   Повторения одной серии связаны (решение владельца 10 октября 2026): серия — по id повторения
   (`gcal.series_of`: `<серия>_<дата>`). Название, категория, приоритет, заметка, изменённые у одного
   (`task_service.SERIES_FIELDS`, только реально изменённые), — у всех незакрытых повторений, а название и заметка —
   ещё и у серии в Google (`patch_series`). Время, Done и удаление — только у одного повторения. Новое повторение берёт
   категорию и приоритет серии; одинаковые названия Groq видит один раз (одна категория).
   Прошедшие события остаются просроченными задачами — так решил владелец 9 октября 2026, не закрывать автоматически.
   Проверки: `scripts/calendar_check.py` (Google и Groq подменены). Любые ошибки календаря (не только `HttpError`: сеть, тайм-аут,
   отозванный токен) логируются и не ломают работу с задачами. В `Credentials` обязательно передаётся `expiry`,
   иначе протухший токен обнаруживается только посреди запроса.
   `PATCH /tasks/{id}` обновляет только переданные поля; явный `null` принимается лишь для
   `deadline`, `note`, `source`, `recurrence_pattern` (`NULLABLE_FIELDS` в `task_service.py`), так снимается дедлайн.
8. Теги берутся из текста только как явные хэштеги, остальное модель выдумывать не должна. С 10 октября 2026 теги
   в интерфейсе не показываются и не редактируются (владелец ими не пользуется); колонка `tags` и разбор остались.
10. Совместные задачи (миграция 014, решения владельца 11 октября 2026). У каждого участника своя копия задачи
   (`tasks`), у всех копий `shared_id` = id главной копии; шаги и комментарии общие и лежат на главной копии
   (`subtasks_service`, `comments_service` отдают их с task_id копии пользователя; у комментария `mine`/`author`,
   удалить может только автор). «С кем» — `GET /people` (остальные допущенные пользователи), приглашение —
   `POST /tasks/{id}/share {user_id}` → `task_invites` (pending) и сообщение в бот с кнопками `sh:y|n:<id>`
   (ответить может только адресат, условное обновление статуса). Принял — копия в его категории «С <имя автора>»
   (у автора — «С <имя>», ставится сама, `partner_category`). Название, срок, «до», место, заметка, приоритет и статус
   меняются у всех копий (`shared_service.propagate`, `update_task(..., propagate=False)` у остальных); галочка
   закрывает у всех, остальным — «✅ … — выполнено (имя)». Удаление = выход (`shared_service.leave`): ушла главная
   копия — шаги и комментарии переезжают к следующей; осталась одна — задача становится обычной. Повтор у
   совместной задачи — 422 (и поделиться повторяющейся нельзя), задачами из Google и платежей не делятся.
   В `GET /tasks` у задачи `shared: {with, pending}` (значок «👥», «⏳ ждёт …»).
11. Место (`tasks.location`, `notes.location`, до 200 символов, миграция 014): в форме задачи и заметки поле с
   подсказками `GET /places?q=` (`placeField` во фронтенде), карта — iframe `maps.google.com/maps?...&output=embed`
   (без ключа), «Открыть в Google Maps» — `google.com/maps/search/?api=1&query=`. Место задачи — `location` события
   Google Calendar; из Google место события приходит в задачу (пустое место в JulYera место события не стирает).
9a. Комментарии к задачам (`task_comments`, миграция 005): `GET/POST /tasks/{id}/comments`, `DELETE /comments/{id}`;
   файл приходит в JSON base64 (фото JPEG/PNG/WebP/HEIC или PDF, до 10 МБ; фото сжимается на телефоне до 1600 px).
   Файлы — в закрытом бакете `task-files` (`<user_id>/<task_id>/<comment_id>.<ext>`), наружу только подписанные
   ссылки на час (`<img>` не умеет слать заголовок входа). Удаление комментария и задачи удаляет и файлы.
   В `GET /tasks` у задачи `comments_count`, `files_count` (значки 💬 и 📎). Бот: фото/PDF → «К какой задаче?»
   (выбор помнится 15 минут в памяти), ответ на сообщение с кнопками `done:/snooze:/cmt:` — комментарий к этой задаче,
   «💬 Комментарий» под «Добавил: …» присылает приглашение ответить (ForceReply).
9b. Просроченная задача: кнопки «На завтра / На послезавтра» под ней в приложении (`moveButtonsEl`, PATCH дедлайна)
   и «➡️ Завтра / +2 дня» в напоминании бота (`mv1:/mv2:<id>`, `digest_service.reschedule`) — сегодня + N дней,
   время прежнее, событие календаря переезжает.
9. Напоминания (`digest_service.reminder_tasks`) берут не-Done задачи с дедлайном до «сегодня + 2 дня» включительно
   по дате пользователя, кроме отложенных (`tasks.snoozed_until` в будущем). Отложенная задача после срока
   напоминается один раз (поле очищается условным обновлением). «Готово» идёт через `task_service.update_task`
   (повтор задачи, календарь). `/today` — просроченное, сегодня и ближайшие 24 часа; `/digest on|off` —
   `users.digest_enabled`; без задач вообще сводка не шлётся. Telegram-команда `/list` показывает только `To Do`.
   Миграция 009 (решения владельца 10 октября 2026):
   - Напоминание перед задачей со временем за `users.remind_before` минут (15 / 30 / 60, 0 — выкл, по умолчанию 30;
     выбор в меню `remindBeforeBox`, `PATCH /me`, бот `/remind`). Не для 23:59 («без времени») и событий на весь день.
     Один раз на задачу и её дедлайн (`pre_reminder_log`, вставка до отправки) — перенесли задачу, напомнит снова.
     Точность ±15 минут (так часто зовётся `/internal/reminders/run`).
   - В воскресенье в слот 20:00 вместо «Итогов дня» — «Итоги недели» (`weekly`): выполнено пн–вс, не закрыто,
     план на следующую неделю по дням, траты недели.
   - В слот 20:00 (если сводки включены) — «💳 Завтра спишется» по активным повторяющимся расходам с

  Прямой `fetch(BASE_URL…)` не добавляй.

  `--chip-color`. Классов по названиям категорий нет. Экран «Категории» в меню: цвет из палитры, название, порядок,

- Telegram Mini App: `telegram-web-app.js`, `ready`/`expand`, цвета шапки и фона из `--bg`, `disableVerticalSwipes`.

## Ошибка загрузки Mini App 7 октября 2026 (диагностика)

Симптом: в Mini App на iPhone в 12:03 по Риму (10:03 UTC) «Сервер не отвечает» и «Не удалось загрузить задачи».
- Исключено: заголовки, запрещающие встраивание (`curl -I /` — нет `X-Frame-Options` и CSP); отказ во входе
  (был бы экран входа; стартовые запросы Mini App под владельцем отвечают 200 за < 1 с: 33 задачи).

  первая неудача сразу давала уведомление; не было повторов на холодном старте и тайм-аута; опрос мог наложиться.
- Причина конкретного сбоя (холодный старт, деплой или сеть) не подтверждена: нужны логи Render за 10:03 UTC.
  Отказы входа сервер теперь пишет в лог одним словом: «нет заголовка», «подпись неверна», «устарел»,
  «не одобрен», «ключ неверный».
- Скриншот 11:50 «Откройте приложение из Telegram» — сайт открыт обычной ссылкой во встроенном браузере Telegram,
  без initData; это ожидаемое поведение.

## Как проверять изменения (автотестов нет)

- Изоляция пользователей: `python scripts/isolation_check.py` (локально, база в памяти, без сети) — все проверки
  должны проходить. С `--base-url https://…` — HTTP-проверки против живого сервиса на временных пользователях
  (нужны настоящие `SUPABASE_*` и `TELEGRAM_BOT_TOKEN` в `.env`; это запись в прод-базу, только с согласия владельца).
  Скрипту нужны все пакеты из `requirements.txt` (в `venv` владельца нет библиотек Google — ставь отдельное окружение).
- Python: импорт и запуск через `fastapi.testclient.TestClient` с фейковыми переменными окружения.
  Обязательно задай фейковые `SUPABASE_URL`, `SUPABASE_KEY` и `GROQ_API_KEY`: без них `database.py`
  и `groq_client.py` падают ещё при импорте. `SUPABASE_KEY` должен быть похож на JWT (например `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJmb28iOiJiYXIifQ.abc`),
  иначе клиент Supabase откажется стартовать. `TELEGRAM_BOT_TOKEN` в тесте не задавай:
  при старте приложение пойдёт в сеть к Telegram. Маршруты с обращением к базе при фейковом URL падают, это нормально.
- JS: вытащи `<script>` из `web/index.html` и проверь `node --check`. На Mac владельца `node` нет:
  тогда проверяй через `osascript -l JavaScript` (`new Function(src)` выдаёт синтаксические ошибки).
- В локальном `venv` нет библиотек Google, поэтому `import main` там падает. Логику `task_service`
  проверяй на заглушках `google_calendar_service` и `supabase`.
- Интерфейс без настоящей базы: `venv/bin/python design/mock_server.py` поднимает `http://localhost:8001`
  с сайтом и подставными данными в памяти. Запускай его через Bash в фоне, а во встроенном браузере открывай
  конфигурацию `mock` из `.claude/launch.json` (она только подключается к адресу). Сам браузер запустить
  сервер из папки «Загрузки» не может: процесс зависает без доступа к файлам.
- Интерфейс проверяй скриншотами в 390 × 844 и 360 × 740 (плюс ноутбук), без горизонтальной прокрутки,
  и сверяй с макетами в `design/reference/`. Кириллица должна рисоваться Onest и Unbounded.
- Встроенный браузер в скрытой панели ставит таймеры и анимации на паузу: проверки с 5-секундной отменой
  удаления делай быстро или через JS в странице, иначе время истечёт раньше клика.
- Правки большого `index.html` делай скриптом, который проверяет, что каждый якорь вставки встречается
  в файле ровно один раз (неуникальный якорь однажды задвоил кусок файла).
